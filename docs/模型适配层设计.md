# 模型适配层设计（Model Gateway）

## 目标

为 AI-ME 提供统一的大模型调用能力：应用层与领域层只面对一种消息模型和一种流式事件协议，厂商差异被完全挡在基础设施层之外。设计参考 [pi](https://github.com/nicepkg/pi) 的 `@earendil-works/pi-ai` 包，取其核心思想，按本项目的 DDD 分层重新落地。

当前范围刻意收窄：只实现两种协议（OpenAI Chat Completions、Anthropic Messages），接入三家厂商（OpenAI、DeepSeek、Anthropic）。其中 DeepSeek 用于验证"新增厂商零协议代码"的扩展方式。

## 从 pi 借来的三个核心思想

1. **协议与厂商解耦**。pi 内置 46 家厂商，但只有约 10 种 API 协议实现；绝大多数厂商只是元数据差异，挂在既有协议上。接入新厂商 = 加一条目录条目，不写协议代码。
2. **统一事件流**。所有协议的输出都翻译成同一种事件序列（`start → 增量 → done/error`），上层只面对这一种表示。
3. **厂商 = 元数据 + 认证 + 协议绑定**。`谁 / 走哪个协议 / base_url / key 从哪读 / 有哪些模型` 全部是声明式配置。

暂不引入的部分：pi 的 compat 兼容开关体系（20+ 个抹平各家 OpenAI 兼容差异的开关）、动态拉取模型目录（`refreshModels`）、OAuth 认证与凭据存储。等真实需求出现再补。

## 分层结构

```text
presentation/api          ChatCompletionRequest (Pydantic，到此为止)
      │  LlmCompletionRequest（统一消息）
      v
application/ports         ModelGateway 端口：list_models() / stream()
      │                    ApiKind 协议枚举、ModelDescriptor 模型元数据
      v
domain/llm                ConversationMessage / Conversation
                          LlmStreamEvent（统一流事件）
      ^
infrastructure/llm        catalog（厂商元数据）
                          ProtocolModelGateway（按 provider/model 分发）
                          openai_completions / anthropic_messages（协议适配器）
      ^
composition.py           build_gateway_from_env()：读环境变量，有 key 才装配
```

与 pi 的对应关系：

| pi (TypeScript)                      | AI-ME (Python)                                    |
| ------------------------------------ | ------------------------------------------------- |
| `AssistantMessageEvent` 事件协议      | `domain/llm/events.py` 的 `LlmStreamEvent`         |
| 消息模型（`ContextMessage` 等）       | `domain/llm/messages.py`                          |
| `Models` 门面接口                     | `application/ports/model_gateway.py` 的 Protocol  |
| `api/openai-completions.ts` 等协议    | `infrastructure/llm/openai_completions.py` 等     |
| `providers/*.ts` 厂商元数据           | `infrastructure/llm/catalog.py`                   |
| `ModelsImpl` + `createProvider` 装配  | `infrastructure/llm/model_gateway_impl.py`        |
| `models.json` 用户配置                | 环境变量（`AIME_*_API_KEY`），暂无配置文件          |

## 核心抽象

### 统一消息（domain/llm/messages.py）

领域内只有一种 `ConversationMessage(role, content)`。`Conversation` 保证至少一条消息。所有协议适配器负责"统一消息 ↔ 厂商请求体"的双向翻译，OpenAI 的 messages 数组和 Anthropic 的 system 独立参数都不会泄漏到这一层之上。

### 统一流事件（domain/llm/events.py）

```text
LlmEventType: START | TEXT_DELTA | THINKING_DELTA | TOOL_CALL_DELTA | DONE | ERROR
```

- `THINKING_DELTA` 对应推理模型的思考内容（DeepSeek 的 `reasoning_content`、Anthropic 的 thinking block）。
- `TOOL_CALL_DELTA` 已预留枚举，翻译尚未实现，等 Agent Runtime 需要 tool use 时再补——那正是它的消费方。
- 错误约定（同 pi）：**流中的异常一律翻译为一条 `ERROR` 事件并终止流，不向上抛出**。因此 SSE 端点对"未知模型引用"这类请求期错误也返回 HTTP 200。

### 端口（application/ports/model_gateway.py）

- `ApiKind`：协议枚举。厂商与协议是多对一关系，DeepSeek 复用 `OPENAI_COMPLETIONS`。
- `ModelDescriptor`：模型元数据（provider、model_id、api、显示名、上下文窗口），全局引用 `ref` 形如 `anthropic/claude-sonnet-4-5`。
- `ModelGateway`：`list_models()` 返回**当前已配置可用**的模型；`stream()` 返回 `AsyncIterator[LlmStreamEvent]`。

### 网关实现（infrastructure/llm/model_gateway_impl.py）

`ProviderRuntime` = 厂商定义 + 已配置认证的协议实例。`ProtocolModelGateway` 按 `provider/model_id` 解析引用并转发到对应协议；解析失败产出 ERROR 事件。`build_gateway_from_env()` 从环境变量读取各厂商 API key，**没有 key 的厂商不进入运行时**，因此 `list_models()` 天然反映可用性。协议 SDK 均为延迟 import，未配置任何 key 时进程不加载 SDK。

### 协议适配器（防腐层）

两个适配器各依赖一个最小 SDK 面（Protocol 只声明 `chat` / `messages` 属性），真实 client 与测试假对象都满足该接口。职责：

- `openai_completions.py`：统一消息 → OpenAI 请求体（system 折叠为首条 system 消息）；分块流 → 事件流，`delta.content` → `TEXT_DELTA`，`reasoning_content`（getattr 探测，兼容 DeepSeek）→ `THINKING_DELTA`。
- `anthropic_messages.py`：system 走独立参数、messages 中不出现 system 角色（`max_tokens` 必填，缺省 4096）；`content_block_delta` 的 `text_delta` / `thinking_delta` 分别翻译为对应事件。

## 一次调用的完整链路

```text
POST /api/chat/completions  {"model": "deepseek/deepseek-chat", ...}
  → routes.py：Pydantic → LlmCompletionRequest（统一消息）
  → ProtocolModelGateway.stream()：解析引用 → ProviderRuntime
  → OpenAICompletionsApi.stream()：序列化 → SDK 分块流 → 翻译事件
  → routes.py：逐事件 json.dumps，以 SSE（data: ...\n\n）返回
```

## 配置

| 环境变量                  | 启用厂商   | 协议                |
| ------------------------- | ---------- | ------------------- |
| `AIME_OPENAI_API_KEY`     | OpenAI     | openai-completions  |
| `AIME_DEEPSEEK_API_KEY`   | DeepSeek   | openai-completions  |
| `AIME_ANTHROPIC_API_KEY`  | Anthropic  | anthropic-messages  |

设置任一变量即启用对应厂商；base_url 等差异由 catalog 中的厂商定义承载，不进环境变量。

## 扩展方式

**新增一家 OpenAI 兼容厂商**（Moonshot、Qwen、本地 Ollama 等）：在 `catalog.py` 加一个 `ProviderDefinition` 并加入 `BUILTIN_PROVIDERS`，配一个新的 `AIME_*_API_KEY` 环境变量，结束。不需要写协议代码。

**新增一种协议**（如 `google-generative-ai`）：四步——在 `ApiKind` 加枚举值；新建 `infrastructure/llm/<protocol>.py` 实现统一消息到该协议的翻译（模块签名参照现有两个适配器，SDK 延迟 import、错误转 ERROR 事件）；在 `catalog.py` 用该协议声明厂商；在 `build_gateway_from_env()` 的分发处加一个分支。

## DDD 立场

- 端口归应用层所有，基础设施实现端口，依赖方向始终向内（由 `tests/test_architecture_boundaries.py` 以 AST 强制，openai/anthropic SDK 只存在于 `infrastructure/llm/`）。
- 适配器即防腐层：厂商协议（消息形状、system 位置、流分块方式、认证）在 `infrastructure/llm` 内完成翻译，领域概念不随厂商变化。
- `llm` 定位为支撑域而非核心域：`domain/llm` 只放稳定不变的概念（消息、事件），不放业务规则。未来的 Agent Runtime 编排逻辑属于应用层用例，模型网关只是它手上的端口。
- 已知的不严格处：`presentation/api/routes.py` 目前直接调用 `model_gateway.stream()` 而非经应用层用例（chat 暂无编排与状态，无伤大雅）。一旦出现会话管理、结果写回工作事项等逻辑，应补 `ChatWithModel` 之类的应用用例，让路由只跟用例说话。

## 测试策略

- `tests/test_model_gateway.py`：以 `SimpleNamespace` 假 SDK 对象覆盖——text/thinking 翻译、system 的两种放置方式（OpenAI 折叠 / Anthropic 独立参数）、异常转 ERROR 事件、按 provider 路由、未知模型引用、目录完整性（两种协议、引用不重复）。
- 架构边界测试保证分层不被破坏。
- 已知盲区：假对象不随 SDK 版本演进（字段变更不会被测试发现）；并发与取消行为未覆盖。建议后续增加带 `skipif(not os.environ.get(...))` 守卫的真实冒烟测试。

## 决策记录

| # | 决策 | 理由 |
| - | ---- | ---- |
| 1 | 错误以 ERROR 事件终止流，不抛异常 | 与 pi 一致；流式场景下调用方只有一种消费方式。代价：请求期错误也返回 HTTP 200 |
| 2 | 有 key 的厂商才进入运行时 | `list_models()` 即可用性，前端无需二次判断 |
| 3 | 暂不引入 compat 开关体系 | 接第三家 OpenAI 兼容厂商遇到真实差异时再补，避免提前设计 |
| 4 | `TOOL_CALL_DELTA` 只预留不实现 | 消费方（Agent Runtime）尚不存在，先定格式不如到时一起定 |
| 5 | 配置只认环境变量，暂无配置文件 | 读取点只有三个；多厂商/多实例需求出现时再上 pydantic-settings 配置类或 pi 式 models.json |
| 6 | 模型元数据硬编码在 catalog.py | 两三家厂商不值得引入 pi 的 JSON 数据目录 + 生成脚本 |
